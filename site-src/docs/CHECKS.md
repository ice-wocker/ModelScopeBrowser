# 自检与守卫

`scripts/check_site.py` 只盯一件事：**构建成功但站点已经坏掉**的问题。
这类错不会自己浮出来——构建是绿的、HTTP 是 200、页面能打开，只是某块地方不对。

## 为什么需要它

这个站点的内容源是手写的 Python 清单。最典型的翻车方式是：

- 改了 repo 名或 APK 文件名 → 站点点进去 404，构建一片绿
- 往 CSS 里插一段没闭合的 `@media` → 之后的规则全部失效，页面变成无样式纯文本
- 把卡片做成整块 `<a>`，里面又有标签链接 → 浏览器把内层链接提到外层之外，卡片被拆碎
- 发新版但忘了重新冻结 `releases.json` → 商店页一直挂着旧版本

这些的错误面都在**运行时**，所以检查必须真的做运行时会做的事：
发 HTTP 请求、数产物、比对 DOM 结构。

## 清单

```bash
python3 scripts/check_site.py                # 完整检查（含外链 HEAD）
python3 scripts/check_site.py --skip-links   # 只查本地结构与一致性（PR 上用）
python3 scripts/fetch_releases.py --check    # 快照是否过期（联网）
python3 scripts/mutate_test.py               # 守卫自证：注入缺陷，自检必须变红
```

## 七类守卫，以及每条真的会怎么红

每条都做过**变异测试**：注入对应缺陷，确认它会红。第一版里有三条是橡皮图章，
写下来是因为「守卫本身失效」比「没有守卫」更危险——它会让人以为已经守住了。

### 一、产物完整性
`sitemap.xml`、`robots.txt`、`feed.xml`、`icon.svg`、`tags.html`、`404.html` 等等。
少一个文件在浏览器里就是 404，而构建本身是绿的。

### 二、样式表能被完整解析
去掉注释与字符串后数大括号，必须配平。

> **真发生过**：插了一段 `@media (prefers-reduced-motion)` 却没闭合，结果它之后
> 的所有规则失效，页面变成没有样式的纯文本。浏览器不报错、文件 HTTP 200、
> 前 6 条规则照样能解析出来——肉眼只在「打开页面」时才发现。

### 三、页面骨架一致性
- 导航项数在所有页面一致（加页面时漏一处，页面上看不出来）
- 主题脚本排在 `<link rel=stylesheet>` 之前（否则深色用户先闪一帧浅色）
- 可索引页面必须有 `canonical`；所有页面必须有 `icon`
- 站内锚点必须存在（标签、技术栈都是页内锚点，拼错就是「点了没反应」）

> 这条守卫的第一版是橡皮图章：它找 `data-theme` 出现在样式表之前——而
> `<html data-theme>` 就在第 2 行，永远在前。现在改成定位内联脚本里那段
> `localStorage.getItem(K)`。

### 四、标签索引双向一致
- 清单里的每个标签都出现在 `tags.html`（少一个 → 首页那颗 pill 是死链）
- `tags.html` 里不许出现清单外的标签（多一个 → 引用了不存在的标签）

### 五、卡片结构：不允许 `<a>` 嵌套 `<a>`
断言首页卡片是 `<div class="card reveal">`，且里面恰好一个 `.cardhit`。

> **真发生过**：整张卡片是 `<a>`，里面又有指向标签页的链接。浏览器不会报错，
> 它当场把内层 `<a>` 提到外层之外——卡片被拆成两半，页面上多出几个
> 「只有技术栈、没有标题」的幽灵方块。而 HTML 源码、构建日志、状态码全正常。

### 六、Release 事实投影
- 商店页每个 APK 的体积、链接、版本号必须与 `releases.json` 一致
- 项目详情页必须显示当前版本（用户从搜索直接落到详情页，看不到就得再跑一趟商店）
- `feed.xml` 条目数必须等于可安装应用数

### 七、下载源配置
- 地区名单必须覆盖 CN/HK/MO/TW 的主要 IANA 时区
- 官方直连必须存在且 `role=fallback`
- 每个加速前缀必须是 `https://` 且以 `/` 结尾（拼接方式是 `prefix + URL`）

> 地区名单那条的第一版也是橡皮图章：它在**文件文本**里找 `Asia/Guangzhou`，
> 而文件注释里正解释着「为什么补它」，文本里一直有。现在从 `exec()` 出来的
> 变量里取。

## 商店页下载层的守卫

下载逻辑坏了在页面上看不出来（按钮在、样式对，只是慢或者下不来），所以必须由检查盯着：

| 断言 | 防止什么 |
|---|---|
| `MAX_PARALLEL` 被赋值且 ≥ 2，且真的出现在发起循环里 | 退化成串行，8 个包排队等建连 |
| 剥掉注释后**不许出现 `fetch(`** | 有人「好心」把已证伪的测速方案加回来 |
| `slowDirect()` 必须被 `return` / 三元 / 赋值调用 | 定义了却不参与决策 = 地区判断没生效 |
| 不许出现 `effectiveType` | 它会被随机报成 3g 导致误开加速，语义也不对 |
| `sourceFor` 里必须有 `i % list.length` | 退化成「所有包押在同一个源」 |
| `candidates()` 必须 `a.concat([d])` | 官方直连不再垫底，失去兜底 |
| 状态条 `#srcbar` / `#srctoggle` 必须存在 | 默认开加速就必须让用户看得见、改得动 |
| 文案里「每批 N 个」必须等于代码里的 `MAX_PARALLEL` | 改了常量忘改文案 |
| 提到「多线程下载」必须同时出现「实测不成立」 | 把已否掉的做法当卖点讲 |

## 更新记录与校验值（新增的两组守卫）

更新记录页和详情页的 sha256 有一个共同点：**错了不会报错，只会安静地骗人**。
用户看到旧版本、看到不存在的「改进了性能」，或者拿到一个永远校验不过的值。

| 断言 | 防止什么 |
|---|---|
| `changes.html` 里每个应用的版本集合 == 快照 `history` | 渲染时丢了一版（用户以为那是全部历史） |
| 页面上版本的**顺序** == 快照顺序 | 倒着读，用户以为最新版是三年前那个 |
| 正文里 `compare/<上一版>...<这一版>` 与相邻条目一致 | 顺序的自证循环：两边同一份数据，一起错时上面那条照样绿 |
| 有正文的版本，第一句必须出现在页面上 | 抓回来了却没渲染（等于白抓，而页面看起来「有内容」） |
| 详情页必须有 `id="changes"` 区块 | 从搜索落地的人不知道还有一整部历史 |
| 详情页「校验安装包」区块里必须有 sha256 | 用户要校验时找不到值 |
| 快照没有 sha256 时，页面不许出现 64 位值 | 编一个值比没有值更糟：用户会以为自己下到了坏包 |
| `update.json` 的 sha256 与快照逐字相同，且必须是 `[0-9a-f]{64}` | 客户端拿它验包，错了就是装不上 |
| `update.json` 必须有 `snapshotAt` | 客户端无法判断这份清单有多新 |
| sitemap 必须含 `changes.html` / `store.html` / `tags.html` | 新页面忘了登记，搜索引擎永远不知道它存在 |

### 首页筛选

筛选坏了的表现很阴：按钮在、样式对，**点了没反应或者筛出空列表**。页面上只是变空白。

| 断言 | 防止什么 |
|---|---|
| 每个有项目的分组都有 `data-filter="group:<slug>"` 按钮 | 加了一个分组却忘了按钮 |
| 带 `data-key` 的卡片数 == 项目数 | 有卡片筛不到（永远隐身） |
| 每张卡片的 `data-key` 覆盖它的全部标签 | 补一个标签进首页标签行，筛选就变成 0 个项目 |
| 每个按钮的 `data-filter` 都能在 `data-key` 里找到对应项 | 拼错一个字符，点下去就是空页 |
| 不许出现 `data-filter="group:"` 这类空键 | 「全部」必须用空串，空键会切出半个键值 → 筛出 0 个 |
| 页面必须有监听 `#filterbar` 的脚本 | 按钮点了不会有反应 |

> 这条守卫里有一半是**在浏览器里点出来的**：先写检查、再去点，才发现
> 「全部」按钮的 `data-filter="group:"` 会让 `slice(0, indexOf(':'))` 与
> `slice(indexOf(':')+1)` 切出半个键，点「全部」直接 0 个项目。
> 静态检查当时是全绿的——因为它只查「按钮存在」。现在这条键的空值规则进了守卫。

## 守卫自证（mutate_test.py）

一个永远不会红的检查，比没有检查更危险：它会让人以为守住了。
所以 `scripts/mutate_test.py` 对产物做**最小改动**（删一个字段、换一个版本号、交换两条），
每次改完跑一遍自检。改了必须红，没红就是守卫失效，脚本以 1 退出。

CI 里的 `guards` job 就跑它——所以「守卫本身」也是被检查的。

## CI 里跑什么

```text
build     构建 → 断言产物清单 → 断言页面数/sitemap 条目 → 再构建一次比对哈希
check     构建 → check_site.py --skip-links（PR）/ 完整检查（每周定时）
releases  构建 → fetch_releases.py --check（快照是否与线上一致）
          → 每周定时额外跑 --verify-digest（声明里的 sha256 vs 真实文件）
guards    构建 → mutate_test.py（逐条注入缺陷，自检必须红）
pages-config  断言域名在 data/ 里只出现一次，且 CNAME 与之相同
```

「再构建一次比对哈希」这条值得单说：纯静态站的承诺之一是可重复构建。
如果哪天有人在渲染里混进 `time.time()`，这条会立刻红——而不是等到某天
「同一个 commit 在两个 CI 上跑出不同结果」时才开始怀疑人生。
