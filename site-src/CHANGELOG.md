# 更新日志

本仓库的改动按日期倒序记录。版本号对应部署，不单独发 Release（站点产物不入库）。

## 2026-11-02

这一轮不加「更多按钮」，加四件**让站点更可信**的事：把每个应用的版本史摊开、
把安装包校验值填上、让首页能就地筛、把「守卫自己有没有失效」也变成 CI 的一部分。

### 1. 更新记录：抓下来的 Release 正文就是一部版本史

`fetch_releases.py` 现在把 `/releases?per_page=10` 的**每一条**都冻结进快照的
`history[]`——这个请求本来就会返回多条，历史不额外花成本。

- 新增 `changes.html`：8 个应用、24 个版本，按应用分组、按发布时间倒序。
- 项目详情页新增「更新记录」，只给最近 3 版 + 「看完整历史」。
- 正文用**自己写的 Markdown 子集**渲染（标题/列表/引用/围栏代码/表格/行内 code·粗体·链接），
  先整体转义、再按白名单放回标记。不支持的一律退化成纯文本，也不引第三方解析库——
  这个站的立身之本是「零依赖，只用标准库」。
- 没有正文的版本（GitHub 自动生成的「Full Changelog: 对比链接」）**明说没写说明**，
  不拿版本号编一句「改进了性能」。当前 24 个版本里 15 个有作者写的正文。

### 2. sha256：现在有了，而且是声明值不是猜的

GitHub 的资产元数据里带 `digest: sha256:...`，`fetch_releases.py` 照抄进快照
（`--verify-digest` 实测过：声明值 == 实际下载文件算出来的值，KayaGo 与 iceReading 逐字节一致）。

- `update.json` 升到 **schema 2**，`latest.sha256` 全部有值；新增 `snapshotAt`，
  客户端可以判断这份清单有多新。
- 项目详情页新增「校验安装包」区块：给出 `sha256sum <文件名>` 与完整值，并说明
  Windows 上用什么命令。没有值的项目——**不显示任何 64 位数字**，并说明为什么不猜。
- 校验真值放在 CI 每周定时任务里跑（`--verify-digest`），常规同步不下载整包：
  为了一个字段每小时把 60+ MB 全下一遍不值当。

### 3. 首页筛选：按分组 / 按标签，就地筛

12 个项目、46 个标签，找一类项目以前只能翻标签索引页。现在首页就能筛：
分组按钮 + 顶部 14 个标签，点第二次取消。**不改地址栏**（否则「返回」会退回上一次筛选而不是离开页面）、
不用 hash（会和分组锚点打架）。没有 JS 时按钮不响应、标签照常跳转，两者都不会坏。

顺带修掉一个自己写出来的坑：最初「全部」按钮写成 `data-filter="group:"`，
`slice(0, indexOf(':'))` 与 `slice(indexOf(':')+1)` 会切出半个键 —— 点「全部」筛出 0 个项目。
浏览器里点出来的，静态检查当时全绿。现在空键本身进了守卫。

### 4. 守卫自证：`mutate_test.py`

一个永远不会红的检查比没有检查更危险。新增 `scripts/mutate_test.py`：
对产物做最小改动（删字段、改版本号、交换两条），逐条确认自检会红，没红就 fail。
CI 里多一个 `guards` job 跑它 —— 所以「守卫本身」也在被检查。
当前 **15 条**守卫全部自证通过。

### 5. 一条不再自证的守卫

版本顺序的检查原本是「页面顺序 == 快照顺序」——两边由同一份数据渲染，一起错时照样绿。
现在多了一条独立证据：GitHub 自动生成的正文里写着 `compare/<上一版>...<这一版>`，
拿它去和页面上排在后面的那一版对。**验证方式**：把快照里两条历史顺序调换再构建，
自检报「v2.7.0 的正文写着自己接在 v2.6.0 之后，但快照里它后面是 v2.5.0」。

### 三个「构建成功但页面明显不对」的缺陷

**① 一条没闭合的 `@media` 让整份样式表失效**

写 `prefers-reduced-motion` 兜底时插了 `@media (prefers-reduced-motion:reduce){` 却没闭合。
CSS 解析器不会报错，它会**从那里开始把后面的规则全部当垃圾**——页面变成没有任何样式的
纯文本，而文件 HTTP 200、前 6 条规则照样能解析出来。**只打开页面才看得出来。**

现在 `check_site.py` 会剥掉注释与字符串后数大括号，必须配平。变异测试验过会红。

**② 卡片整块是 `<a>`，而卡片里还有链接**

技术栈做成了指向标签索引的链接，卡片本身是指向详情页的 `<a>`。HTML 不允许
`<a>` 嵌套 `<a>`：浏览器不报错，它**当场把内层 `<a>` 提到外层之外**，于是卡片被拆成两半，
页面上多出 4 个「只有技术栈、没有标题」的幽灵方块。

改成容器 + 绝对定位的整卡点击层（`.cardhit`）+ 标题真链接。键盘用户 Tab 只停一次，
读屏读的是 `aria-label`。守卫断言「首页不许出现 `<a class="card">`」——
第一版守卫只数 `.cardhit` 的个数，改回整卡 `<a>` 时依然全绿，是橡皮图章。

**③ 入场动效可能让内容永远不可见**

`.rv{opacity:0}` 由 JS 挂上，再等 IntersectionObserver 加 `.on` 才显示。
回调没来时——后台标签页、无头浏览器、某些 WebView——卡片**永远停在透明**，
控制台一声不响。现在改为「先挂 `<html class="js">`，隐藏态依赖它」，
并带一条 1.2 秒的 CSS 动画兜底：即使回调一次都不来，内容也会自己淡入。
打印样式里直接 `opacity:1 !important`。

> 附带发现的第四个问题：`.rv` 是挂在 `<html>` 上的类选择器，写成
> `html.js .rv` 会让**页面里每一个**带该类的元素（包括卡片内的每个 `<span>`）都成为
> 待淡入元素。改成专用类 `.reveal`。

### 站点本身

**主题真正做成三档。** 之前只有一套深色变量，`color-scheme` 却写着 `dark light`——
浅色系统用户看到深色页面，而地址栏按浅色画，视觉上是断的。现在 `:root` 深色、
`[data-theme=light]` 与 `prefers-color-scheme: light + theme=auto` 两处覆盖，
变量名不变所以组件样式一处没动。切换按钮三档循环，选择存 `localStorage`，
内联脚本排在样式表**之前**执行，首屏不闪。

**可被抓取。** `canonical`、`og:url`、`og:site_name`、`twitter:card`、`sitemap.xml`、
`robots.txt`、RSS（按发版推送）、JSON-LD（`WebSite` + `ItemList` + 每个项目的
`SoftwareApplication`），以及手写的 `icon.svg`。此前全站 12 张页面共用同一句 description，
分享出去就是一块白板。

**新增标签索引页。** 46 个标签，按项目数排序，两列布局 + 页内锚点跳转。
首页的标签行、卡片的技术栈都链到这里。守卫做双向校验：清单里的标签一个不少，
页面上也不许多出清单外的。

**详情页补 Release 事实。** 之前版本号/体积只在商店页显示，用户从搜索结果直接落到
详情页时看不到，得再跑一趟商店。现在版本、体积、最低系统、ABI、发布时间、下载数
都在详情页顶部。

**搜索**：中文按二元切分（「推理」能命中「本地推理」）、上下键 + 回车 + Esc、
`fetch` 失败时明确提示并给出标签索引作为兜底入口——而不是变成一个「输什么都没反应」
的死控件。

**404 页带搜索框**：会撞上 404 的人手里有词（旧的项目名），不该被要求自己一层层点回去。

**可访问性**：「跳到正文」链接、`:focus-visible` 焦点环、卡片点击层带 `aria-label`、
搜索框 `role=combobox` + `aria-selected`（高亮不只靠颜色）。

## 2026-09-30（第二次）

### 修「下载速度还是不行，而且链接经常失效」

用户反馈上一轮的按地区选源之后仍然慢、且链接会失效。实测复现了两件事。

**① 链接失效的真凶：`ghproxy.net` 在 61 MB 包上 3/3 次下不完**

同一个 61 MB 包，连测三轮：

| 源 | 第一轮 | 第二轮 | 第三轮 |
|---|---|---|---|
| 官方直连 | 61,130,620 B / 9.8 s | 完成 / 10.3 s | 完成 / 10.6 s |
| gh-proxy.com | 完整 / 9.8 s | 完整 / 9.8 s | 完整 / 9.9 s |
| ghfast.top | 完整 / 13.6 s | 完整 / 31.9 s | 完整 / 14.6 s |
| **ghproxy.net** | **只到 3.6 MB 就超时** | **只到 2.9 MB** | **只到 4.3 MB** |

`ghproxy.net` 小包（168 KB）能下完，大包必挂——而它此前**还在候选列表里**，
一旦被选中，用户看到的就是「链接失效」。已从 `data/mirrors.py` 移除。

**② 慢的结构性原因：8 个包全押在同一个源上**

旧实现 `pickSource()` 只返回**一个**源，8 个包全走它。所以源一限速，
不是「某个包慢」，而是「整批一起慢」。这才是「速度还是不行」的放大器。

改成**多源轮转**：按包下标把 8 个包分摊到各候选源（加速源 + 官方兜底）。
浏览器实测分布 `gh-proxy.com 3 / ghfast.top 3 / GitHub 官方 2`——
单源挂掉最多影响其中 3 个，而不是全灭。

**③ 「自动重试」做不到，这点必须说清楚**

页面**无法自动知道**某个包有没有下成。下载走 `<a>` 导航，跨域读响应被 CORS 挡死：
直连与三个反代**都不带 `Access-Control-Allow-Origin`**，`no-cors` 只能拿到
opaque response（`status=0`、`type=opaque`）。实测确认——无论包存在与否、
源是否超时，`fetch` 都在 10~20 ms 返回，**读不出任何差异**。
所以不写「自动重试」，而是给每个包一个**「换源重下」**按钮：
没下下来就点它，换下一个候选源立即重下，不用整批重来。浏览器实测
`gh-proxy.com → ghfast.top → GitHub 官方` 推进正确。

**顺带修的文案 bug**：状态条把「候选源数」写成了「分担包数」，
实际是「8 个包分给 3 个源」。

`check_site.py` 新增 7 条守卫（多源轮转、换源重下、官方兜底排序等），
逐条做过变异测试确认能变红。

## 2026-09-30

### 下载源按地区自动选，「加速默认开」但完全透明

用户反馈「官方直连太慢，应该默认开加速或按地区选源」。

**做法：按地区选，不测速。** 直连 GitHub 的体验按地区两极分化，且差异稳定——
大陆普遍几百 KB/s 甚至断流，海外接近满速。稳定差异可以在本地推断，零请求：
读时区（`Intl.DateTimeFormat`）与语言/地区（`navigator.language`）。
命中则默认启用加速，否则默认官方直连。

**刻意不看网络类型**：第一版加了「`effectiveType` 是 2g/3g 也走加速」，
实测有问题——headless Chromium 会随机把 `effectiveType` 报成 3g（同一个
Tokyo / ja-JP 上下文 5 次里 1 次），加速因此被误开。更要紧的是语义不对：
它说的是「我的链路慢」，不是「我到 GitHub 远」，慢链路上反代同样慢。
已去掉，并加了守卫防止捡回来。

**为什么不测速**：上一轮已经证明 `fetch` 探针读不到数据（CORS），
那部分结论不变，`fetch` 守卫也保留。

**透明性是默认开加速的前提**：
- 页面顶部新增下载源状态条，显示当前源 + 为什么这么选
- 一键切回官方直连，选择存 `localStorage`，重载保持
- 加速源打不开时显式回退并在界面说明，不静默降级
- `data/mirrors.py` 用 `role: fallback` 标记官方兜底源，不允许删

**顺手修掉两个既有缺陷**：
- 商店页有两个重复的 `<h2 id="speed">`，第二段还在描述已被撤掉的 fetch 测速
  （文案在讲一个根本不存在的功能）。合并为一节，并把「并行发起 5 个」与实际
  代码交叉校验——原来的守卫拿常量 `5` 当基准比文案，改 `MAX_PARALLEL` 时永远为真。
- `slowDirect 是否被调用` 的守卫第一版是橡皮图章（函数声明本身就能匹配上），
  改成断言调用出现在赋值/条件上下文，注入「永不调用」确认会变红。

`check_site.py` 新增 7 条守卫（含「不得用网络类型做地区判断」），全部做过变异测试。

### 下载速度：从「串行等建连」改为「并行发起」(#4)

用户反馈下载慢。根因不是带宽，是页面在串行点链接——8 个包一个接一个，每次都要重等一遍建连。

动手前先量了三件事：

- **多线程分块下载无效**。同一文件开 1 / 2 / 4 条连接，总吞吐都是 ~6.2 MB/s，
  说明单连接吞吐固定。所以没做这个功能。
- **并行建连有效**。单连接速度依赖文件大小（58 MB 是 2.4 MB/s，0.07 MB 只有 0.78 MB/s），
  小包慢在建连而非带宽。并行后总吞吐是各连接之和。
- **自动选最快镜像做了又撤掉**。`fetch` + `Range` 探测四个候选，全部读不到数据——
  GitHub Release 302 之后的 `release-assets.githubusercontent.com` 不带
  `Access-Control-Allow-Origin`，三个反代同样不带，计时恒为 0。
  它失败得很安静（探针全失败后退回直连，页面照常下完），所以撤掉并加了守卫禁止 `fetch` 回来。

新增 `data/mirrors.py`（默认只走官方直连），商店页新增「下载速度」小节把实测数字摊开写，
`check_site.py` 增加 6 条守卫，全部做过变异测试。

### 应用商店 (#2 #3)

- 商店页上线：8 个应用 + 一键下载全部，体积/版本来自 Release 快照而非手写
